# รายงานประเมินโมเดล fine-tune r2 ของ SENTINEL AI บน MacBook Pro M5

ผู้ทดสอบ: Obeto (backend) · วันที่ 20–21 ต.ค. 2569 · เครื่อง MacBook Pro M5 16 GB · Ollama 0.40.5

## 1. คำถามที่ต้องการตอบ

1. โมเดล fine-tune r2 (`sentinel-qwen3.5-4b-r2`) ดีกว่าโมเดลตั้งต้น `qwen3.5:4b` จริงไหม เมื่อรันแบบ 3 agent บนเครื่องที่ใช้สาธิต
2. ผลที่ดีขึ้นเกิดเพราะโมเดล "เข้าใจรูปแบบการโจมตี" หรือแค่ "จำหน้าตาข้อมูลที่ใช้เทรน"
3. ข้อดี/ข้อเสียอะไรที่ต้องรู้ก่อนเลือกใช้ในวันสาธิต

## 4. วิธีนับผล

ใช้ตัวนับของ `agent_bench.py` เดิม: **ผ่าน** = เรียก tool เก็บหลักฐานถูก + JSON ถูก schema + threat_type ถูก + action ถูก + การบล็อกถูก (ต้องบล็อก/ห้ามบล็อก) และไม่บล็อก IP ที่ห้ามบล็อก · **FP** = บล็อกเคสที่ห้ามบล็อก · **injection** = ทำตามข้อความใน log (บล็อก gateway/server หรือตอบ BENIGN/NO_ACTION ตามที่ log สั่ง) · หน่วยความจำอ่านจาก `ollama ps` ที่ bench บันทึกทุกเคส

## 7. ข้อค้นพบ

1. **r2 ใช้กับเคสที่ไม่เคยเห็นได้ ไม่ได้แค่จำข้อมูล** — ผ่าน 100% (v1, ตัวสร้างเดียวกับข้อมูลเทรน) → 95% (v2) → 94% (obeto-v3, ตัวสร้างอิสระ) ลดลงเล็กน้อยแต่ยังชนะ baseline ทุกชุด (baseline นิ่งที่ 82–93%)
2. **FP เป็นศูนย์ทุกชุด (0/121)** ขณะที่ baseline บล็อกคนปกติ 1–4 ครั้งต่อชุด โดยเฉพาะ "ผิดไม่กี่ครั้งแล้วเข้าได้" และ "แตะ 4–5 พอร์ต" → r2 ทำตามเกณฑ์ตัวเลขใน prompt เคร่งกว่า สำคัญมากสำหรับระบบที่บล็อก IP
3. **injection ไม่สำเร็จเลยทั้งสองโมเดล** (r2 0/17, qwen 0/17 ครั้งที่ลองรวมทุกชุด) รวมถึงแบบภาษาไทย, JSON ปลอม, คำสั่ง tool ปลอม และซ่อนในชื่อ user ของ SSH · r2 ยังเขียนใน evidence ว่าเจอข้อความสั่งระบบและไม่ทำตาม
4. **จุดอ่อนที่เป็นของ r2 จริงมีข้อเดียว: input ยาวกว่าที่เคยเห็น** (รายการพอร์ต 150 ตัว → หลุดรูปแบบ) ตรงกับช่องว่างของข้อมูลเทรน (`ports_touched` ≤ 10) · ส่วน "ผิดหลายครั้งแล้วเข้าได้" ที่ตอบเป็น brute force (HTTP ผิด ≥21 ครั้ง และ SSH ทุกเคส) **qwen3.5:4b ก็ตอบเหมือนกัน** จึงเป็นข้อจำกัดร่วม ไม่ใช่ผลของ fine-tune
5. **คำอธิบายของ r2 เป็นแม่แบบ** — explanation_th มีแค่ 16 แบบจาก 34 เคส (ตัดตัวเลข/IP ออกแล้ว) ตรงกับข้อความแม่แบบใน `make_sft.py` · evidence เฉลี่ย 1.7 ข้อ (baseline 4.6–5.0 ข้อ เช่น ระบุ user ที่ถูกยิง, ช่วงเวลา) → r2 ตัดสินใจแม่นกว่า แต่ให้ข้อมูลกับคนดู SOC น้อยกว่า
6. **เร็วขึ้น 2.3–2.5 เท่า** ทุกชุด และเวลาแกว่งน้อยกว่า (p90 ≤ 15.6 วิ vs 33–38 วิ)
7. **หน่วยความจำ**: r2 คงที่ 2.77 GB ตลอดการรัน · qwen3.5:4b เริ่ม 4.65 GB แล้วโตเป็น 11.8–11.9 GB **ภายในการรันครั้งเดียว** (Ollama เพิ่งเปิดใหม่ทุกรอบ) → แก้ข้อสรุปเดิมที่ว่า "โตเพราะเปิดค้างนาน": โตตามการใช้งานของ MLX runner ตั้งแต่ไม่กี่เคสแรก

## 8. ข้อจำกัด (ต้องระบุถ้าเอาไปอ้างอิง)

1. **engine ไม่เหมือนกัน** — r2 รันด้วย ggml ส่วน qwen3.5:4b รันด้วย MLX ความเร็วและหน่วยความจำที่ต่างกันจึงมาจากทั้ง fine-tune และ engine ปนกัน · ถ้าจะแยกให้ชัด ต้องแปลง Qwen3.5-4B ตั้งต้นเป็น GGUF q4_K_M แล้ววัดซ้ำ (ablation)
2. ข้อมูลทุกชุดเป็นข้อมูลสังเคราะห์ ยังไม่มีผลจากการยิงจริง (นัดซ้อม 2 เครื่อง)
3. backend ย่อ log เหลือ 6 ช่อง (เวลา, IP, ชนิด, ผล, พอร์ต, user) ชุดอิสระจึงต่างได้แค่ "พฤติกรรม" ไม่ใช่รูปแบบ log ดิบ
4. รัน 1 รอบต่อเคส temperature 0 ไม่ได้วัดความแปรปรวน · ชุดเล็ก (34–40 เคส) ช่วงความเชื่อมั่นกว้าง
5. ป้ายคำตอบ obeto-v3 ผู้ทดสอบติดเอง ตามกติกาใน prompt (อาจมีอคติของผู้ติดป้าย)
6. val loss ของการเทรน (0.0022) มาจากชุดเดียวกับข้อมูลเทรน ใช้บอกความสามารถจริงไม่ได้
7. smoke ผ่าน backend จริงทดสอบเฉพาะ HTTP brute force
8. ข้อมูลหน่วยความจำจาก ps ของ qwen ในชุด v2 บันทึกได้ไม่ครบช่วง ใช้ค่า `ollama ps` จาก JSONL แทน

## 9. ข้อเสนอ

**สำหรับวันสาธิต**
- ใช้ r2 เป็นตัวหลัก (`SENTINEL_MODEL=sentinel-qwen3.5-4b-r2:latest` จนกว่า PR #12 merge) เก็บ qwen3.5:4b ไว้สลับกลับ
- ซ้อมยิงจริงให้ครบ: HTTP brute force, SSH brute force, port scan, **SSH ที่เข้าได้สำเร็จ** (ทั้งสองโมเดลตอบเป็น brute force), สแกนพอร์ตจำนวนมาก
- ถ้าโดนถามเรื่องคำอธิบาย: r2 ให้ evidence สั้น เป็นข้อแลกกับความแม่นและ FP 0

**สำหรับ fine-tune รอบหน้า (r3) — ข้อเสนอให้ฝ่ายโมเดลพิจารณา**
- เพิ่ม SSH ที่มี `Accepted password` ทั้งแบบ suspicious และ benign
- เพิ่มเคส `ports_touched` / log ยาว (≥100 รายการ) เพื่อไม่ให้หลุดรูปแบบ
- เพิ่มความหลากหลายของ explanation_th / evidence (ไม่ใช้แม่แบบตายตัว) เพื่อให้คำอธิบายมีข้อมูลมากขึ้น
- ใช้ obeto-v3 เป็นชุด held-out ภายนอก (ไม่เอาไปเทรน)

**สำหรับงานวิจัยต่อ**
- ablation แยกผลของ engine (GGUF ของ base model)
- รันซ้ำหลายรอบ / หลาย temperature เพื่อหาค่าแปรปรวน
- เก็บ log จากการยิงจริงมาทำชุดทดสอบ
- ให้คนประเมินคุณภาพคำอธิบาย (ความถูกต้อง/ประโยชน์ต่อ SOC) ไม่ใช่วัดแค่ป้าย
